# AI 构筑锻造设计

## 设计目标

让 AI 参与每局的武器构筑，而不是接管自动战斗。玩家继续负责走位和商店选择；武器继续自动索敌、自动攻击。AI 的职责是在商店阶段理解玩家想要的打法，并把它转成游戏已经支持、能看懂、能购买的武器改造。

设计成功的标准：玩家不必输入提示词，系统根据本局状态给出的候选确实改变武器攻击行为；不合规、冲突、角色不能使用或当前没有的改造不会进入购买流程；断网或 AI 出错不阻断游戏。

## 核心循环

```text
玩家已有角色 / 武器 / 改造 / 道具
        ↓ 商店阶段点击构筑推荐（无需输入文字）
AI 从授权的改造目录中选择/组合候选（不生成代码）
        ↓
本地校验：角色限制、持有武器、互斥组、前置条件、预算边界
        ↓
三项商店预览：当前效果 → 改造后行为 → 代价/取舍
        ↓ 玩家确认购买
写入本局 WeaponInstance 的改造 ID
        ↓
自动战斗按改造后的确定性规则运行
```

AI 只在商店调用，不在 Update、瞄准、开火、命中或敌人移动中调用。单局已确认的改造是本地确定状态，不能因为每帧请求或网络结果变化而改变。

## 构筑语言

构筑由三层组成：

1. **武器形态**：改变攻击本身，例如土豆剑从向外挥砍改为向前刺击；不是只把伤害乘一个系数。
2. **联动部件**：改变攻击与其他事件的关系，例如某类攻击命中后触发另一个已实现的效果。
3. **支撑选择**：角色特长、道具和属性，强化或补足这条路线。

首个验证曾只实现一把土豆剑、一种行为改造。现在已扩至多种 SO 候选；后续改造逐把加入，必须复用已有动画、命中判定和效果组件；AI 不得创造项目中不存在的攻击形状、特效或脚本行为。

## 商店规则

- 商店仍只有三个位置，刷新、锁定、购买/出售和现有武器槽逻辑保持不变。
- AI 构筑改造占用这三个位置之一，不另加第四栏或强制弹窗。
- 候选池优先考虑当前持有且角色允许的武器；未持有武器的改造不显示。
- 每项预览说明：改造目标、攻击表现变化、适用条件、明确的取舍、价格和与已有改造的关系。
- 同一互斥组只能选一种形态；满级、重复、冲突、角色禁用或买不起时不能确认购买。
- AI 没有返回有效候选时，商店回退到现有确定性商品池，不显示伪造的“AI 建议”。

## AI 的输入与输出

输入只含完成本次推荐必要的结构化状态：角色 ID、当前波次和材料、持有武器与改造 ID、持有道具 ID、当前允许的改造候选。默认不发送姓名、设备标识或本地存档全文，也不要求玩家提供提示词。

AI 输出结构化的候选 ID 列表和简短解释。候选 ID 必须存在于本地 `WeaponForgeCatalogSO`；游戏端以 SO 为唯一真相，忽略 AI 自创的名称、数值、价格和效果字段。AI 不输出可执行代码、脚本、任意反射类型或 Unity 资源内容。

每张卡由确定性本地数据渲染。AI 的自然语言解释只是附加说明；效果、代价、购买有效性全部以本地验证结果为准。AI 不能自动购买、消费材料、改存档或绕过玩家确认。

## ScriptableObject 配置边界

所有设计师可调内容放在 SO：改造 ID/名称/说明/图标、适用武器与类别、攻击模式变更、互斥组、前置条件、效果组件 ID、代价/副作用、可出现商店阶段、AI 是否可推荐及推荐标签。数值平衡后续单独配置，不在本轮定案。

SO 提供有限、显式的改造组件；运行时武器实例仅保存已选改造 ID 与实例级状态。严禁直接改写共享 `WeaponData` 或 SO asset，避免一个玩家购买后污染其他实例或下一局。

## 离线、延迟与安全

- 调用仅发生于商店；超时/失败可取消，不扣材料，不改构筑，不挡“下一波”。
- 离线选项使用有明确标签的本地候选生成器；UI 不得把本地随机结果冒充真实 AI。
- 若发给朋友的版本要连接商业模型，API 密钥不能硬编码进 Unity 客户端；需由受控服务代理或由玩家自行配置凭据。正式选择模型、服务端部署和费用策略是单独决策。
- AI 结果必须经过本地 schema、语义和状态校验；任何未知字段/ID/超范围结果都拒绝。

## 验证与迭代

每次记录匿名的构筑结果指标：候选 ID、是否购买/刷新/锁定、购买后武器实际使用情况、通关/死亡波次。日志用于发现无用或过强的组合，不直接让模型自行改平衡。所有 AI 推荐仍需人工试玩。

## 当前最小闭环实现状态（2026-09-24）

- `GameContentSO.weaponModifications` 是改造目录；当前只有土豆大剑“磨锋：直刺”一项，价格为 0 时继承武器基础价。
- 购买后只把改造 ID 和有效攻击动画写入该把 `WeaponInstance`，不修改共享武器 SO；武器可视攻击帧与原近战命中检测继续共用。
- 构筑改造会替换一个未锁定商店位置，不增加商店栏位；锁定改造跨波保留，但若目标武器已不再兼容，则下次开店清除失效报价。
- `GameSettingsSO.weaponForgeEndpoint` 为空时，商店提供“本地改造测试”，按目录 ID 顺序选择一个可用候选，并明确标注“本地目录建议（非 AI）”。这条路径用于不依赖联网验证购买与攻击行为。
- 配置 HTTPS 后端后，按钮切换为 AI 建议；后端只需返回候选 ID 列表和解释，客户端重新校验候选仍合法，卡片内容、效果和价格仍读取 SO。客户端不含模型密钥。
- `验证脚本/ai_build_forge_mvp.mjs` 是独立确定性 fixture 验证，不代表真实模型或 Unity Play Mode。C# 编译通过；Play Mode/画面交互仍需在已打开的 Unity 编辑器里手工检查。

## DeepSeek 本机接入进度（2026-09-29）

- `UnityProject/Tools/deepseek_forge_proxy.py` 是仅监听本机的可选代理。Key 在启动时隐藏输入或来自环境变量，不写进 Unity；代理按 DeepSeek JSON 输出格式请求模型，并再次校验候选 ID 属于本次本地目录。
- Unity 异步返回增加商店版本检查：离开商店、刷新、锁定、购买或重开后，旧建议不会覆盖新商店状态。客户端还限制了响应大小、候选数量与 ID 格式。
- `UnityProject/Tools/test_deepseek_forge_proxy.py` 使用假响应完成 4 项离线契约测试；C# 编译通过。尚未使用真实 Key 调用 DeepSeek，也尚未完成 Unity Play Mode 交互验证。
- 该代理不能直接给手机朋友使用。远程接入需要单独部署受控 HTTPS 服务，并设置访问控制与调用限额。操作步骤见 `docs/AI接入DeepSeek本机测试.md`。
- 用户为临时测试明确选择了将受监控的测试 Key 内置 Unity；`GameSettingsSO.weaponForgeApiKey` 非空时会优先直连 DeepSeek Chat Completions，解析 JSON 候选后仍执行客户端目录白名单与商店状态校验。该模式不保护 Key，测试后应清空并撤销测试 Key。尚未使用真实 API 或 Unity Play Mode 验证。
- 当前构筑入口不再要求玩家输入文字。商店按钮依据角色、武器、道具、波次和材料推荐最多两个既有改造，占用三格商店中的未锁定位置；11 条 SO 改造覆盖剑/拳的前向波、枪弹弹墙和穿透等路线，伤害与攻速代价可在 SO 调整。运行时不让模型生成代码或新素材。

## 分阶段交付

1. **闭环原型**：一个固定意图、一个合法土豆剑改造；贯通候选、验证、预览、购买、运行时攻击形态变化，并验证非法候选被拒。
2. **固定目录**：以 SO 配出少量行为改造，商店可在三项中抽取；断网可玩。
3. **真实 AI 候选**：仅允许模型在现有目录中选/组合候选，接入 provider、结构化 schema、超时、校验、分析记录和明确的玩家确认。
4. **试玩迭代**：逐个武器扩充，验证选择是否真改变走位与目标处理，而非只提高 DPS。

## 本轮明确不做

不改变角色槽位、敌人职责、Boss 通关条件、波次或整体数值；不生成新素材；不让 AI 实时操控敌人或玩家武器；不将未经验证的随机数值写进 SO。
